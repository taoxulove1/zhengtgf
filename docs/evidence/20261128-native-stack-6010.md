## 1. Super 绑定失败的真因（ifname 语义）

`native_trial.sh` 两次实跑 21:28 成功 / 22:04 失败，曾误判为「启动时序不稳」。
用 `tools/probe_super_bind.sh` 单变量实验拆开，其实是**两个独立问题叠加**：

1. **A（真因）**：`<ifname>10.1.0.10</ifname>` 是 IP，而 `zSocket::getIPByIfName()`
   走 `ioctl(SIOCGIFADDR)` 只认网卡名 → 返回 `0.0.0.0` → 原生栈报
   「本机 IP 不正确 0.0.0.0, 10.1.0.10」直接退出，**根本没走到 bind**。
   Wine 原版反过来只认 IP，所以两种栈不能共用一份 config.xml。
   实测网卡名是 `eth0`（`ip -o -4 addr` → `eth0 10.1.0.10/22`）。
2. **B（伪因）**：22:04 日志停在 `zTCPServer::bind`「不能绑定服务器端口」是 A 的次生
   现象（当时配置处于半切换状态）。python 直连 `bind(0.0.0.0,10000)` 实测端口干净。

## 2. 启动顺序：FL 必须先于 Super

`SuperService::init()` 里 `FLClientManager::init()` 建 `FLClient(10.1.0.10:8001)`，
4s 后首次 connect，连续失败两次就 `finalHandle()` 退出；Scenes/Record 等又要连 Super(10000)，
Super 一死全链崩——22:04 的 6010 缺席是这一连锁的下游。
最终顺序（`tools/native_boot.sh`）：

```
FLServer → SuperServer → MiniServer → RecordServer → BillServer
        → SessionServer → GatewayServer → ScenesServer
```

Gateway 若起太早，会停在 `zSubNetService::setServerInfo` 等 Super 的 verify——
Super 的启动依赖序列里 Gateway 依赖 Scenes，Scenes 没验证通过就不发 verify。
boot 脚本对 6020/10000 做了一次补偿重启。

## 5. 缺失配置 XML（逐个从 init 失败日志逼出来）

日志中文被 log4cxx 在 C locale 下转成字面 `?`，按 `?` 段长度反查源码格式串定位：

| 缺失文件 | 证据 | 处置 |
|---|---|---|
| `Config/Mall.xml` | 根 `<wares>`，item(id,kind,action) | 仓库 `src/server/Config/` 全套上传 |
| `Config/FuBenConfig.xml` | 根 `<Config>`，FuBen 节点 | 同上 |
| `Config/ShenJianConfig.xml` 等 17 个 | fjconfig.cpp 21 个 initFile | 仓库全套（15 个）+ 空壳 9 个 |
| `messageSystem.xml` | config.xml 的 `messageSystemFile` 指向工作目录根 | 仓库 MessageSystem.xml 复制改名 |
| `Config/ZuoQiTuJianConfig.xml` | fjconfig.cpp:548，根 `<config>` | 空壳 |
| `./GiftBoxConfig.xml` | GlobalBox.cpp:63，根 `<giftboxs>`，I/O warning 实锤 | 空壳 |

`?` 段计数法：log4cxx 每个中文字（GBK 2 字节）输出 2 个 `?`。
如 `[14,4]` = 7 字 + `...` + 2 字 = 「初始化宝箱模块...失败」。

## 6. luabind/liblua 双重 ABI 修复（第二只崩溃，最隐蔽）

gdb 抓到 `Binder::bind(LuaVM*)` 注册 luabind 模块时跳野地址
`0x08693538 boost::function1::stored_vtable`，栈里混着
`/usr/local/include/boost-1_33_1` 与 `p3-scenes-boost-fix/include`(1.34.1) 两套头。
事实：`libluabind.a`（p3-lua-deps 预编产物）按已不存在的 Boost 1.33.1 编，
而仓库自带 luabind 源码（`src/client/luabind/src/*.cpp`）+ 客户端 Boost 1.34.1。

处置（`tools/rebuild_luabind.sh`）：用 1.34.1 重编 `libluabind.a`（19 个 cpp，318KB）
替换 p3-lua-deps 旧库（备份 `.bak-133`），ScenesServer 全量清编（8.1MB→5.1MB）。

## 7. Lua 5.1 词法器 GBK 标识符补丁（第三只崩溃）

newquest 脚本大量使用中文标识符（`local menu_848_领取装备`、`function 领取装备()`、
`消息(当前角色,17,"...")`），本来就是给「支持 GBK 标识符的私有 Lua」写的。
api.github.com 拉 `lua/lua v5.1.1`（tarball 132KB），给 `llex.c` 打两处补丁
（`tools/fix_lua_gbk.sh`）：

- 入口：`isalpha(c)||c=='_'` 增加 `c != EOZ && (unsigned char)c >= 0x81`
- 扫描循环：lead(0x81-0xFE) + trail **无条件成对消费**（尾字节 0x40-0x7E 也合法），
  循环条件同样带 `!= EOZ` 守卫

两个踩坑记录：
1. 首版按「trail ≥ 0x81」消费，遇到尾字节 0x40-0x7E 的字（如 `…7D`）错位，
   报 `'end' expected near 'end?5'`；
2. 首版没排除 EOZ，`(unsigned char)(-1)=0xFF ≥ 0x81` 在 EOF 处误判成 GBK lead，
   词法死循环（表现也是 `near 'end?'`）。

用补丁版解释器批量校验：`newquest/` 全部 lua **语法错误 0**。
`liblua.a`（246KB）替换 p3-lua-deps 旧库（备份 `.bak-orig`），ScenesServer 重链。
此前对 35 个脚本做过标识符 ASCII 清洗（`tools/sanitize_lua_ident.py`，备份 `.bak-cjk`），
词法器补丁生效后**全部还原**，保住原语义。
