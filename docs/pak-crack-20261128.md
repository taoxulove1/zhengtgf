## 2. XPAK 格式（源码 PackAggregate.cpp 实证）

```
stPackHeader 20B : magic "XPAK" | version(9/8) | filenum | headerSize | flag
flag             : 1=Compress 2=Encrypt 4=EncryptHeaderOnly
stFileInfo1 20B  : dwFileID | fileOffset | size | interspaceSize | dwCRC
索引             : 每条 stFileInfo1 + name\0，总长按 8 对齐，用 HeaderData_DES_SPtrans 3DES
数据区           : stFileSizeInfo{version, flags, uncompressedSize, dwCRC}(16B, 自身也加密)
                   + 载荷（raw deflate，加密时按 8 字节补齐）
fileOffset       : 相对数据区起点（文件头 20B 之后）
dwFileID         : CRC32(name 小写、反斜杠转正斜杠)，初值 0xFFFFFFFF，无 final xor
infoH.dwCRC      : CRC32(加密后的载荷, seed=CRC32(加密后的 stFileSizeInfo))
fInfo.dwCRC      : CRC32(原始未压缩数据)
```

密码不是 `20210112taozhi`（那是 2022 源码里的默认值），实际包用的是 `xuzhao20041108`。

## 3. 3DES 移植要点（本次纠错）

`EncDec/source/mydes.cpp` 是 OpenSSL 风格实现，易错点三处：

1. **`IP` / `FP` 是文本宏**，调用点 `IP(r,l)` / `FP(r,l)` 会把调用者变量名换进宏里，
   宏内 `l` 实际是调用者的 `r`。移植时参数角色必须按宏展开对齐，不能按函数语义。
2. **子密钥循环里的 28 位旋转**：C 里 `c=((c>>2)|(c<<26))` 是在 28 位掩码内旋转，
   不是 32 位 `ror`。用 32 位旋转会丢位。
3. **`DES_encrypt2` 没有 IP/FP**，只有首尾的 `ROTATE(…,29)` / `ROTATE(…,3)`；
   IP/FP 只在 `DES_encrypt3/decrypt3` 里各做一次。

自检：`python tools/des_mydes.py` → `roundtrip SP_HDR: True / SP_DATA: True`。

## 6. 卡点分析

- 报文文案与 `datas\sound.ini`、`data\datas.pak` 字符串在内存里相邻
  （`0x00cdffb0` / `0x00cdffc0` / `0x00cdffd0`），提示该校验发生在"从 datas.pak 取
  sound.ini 一类文件"的代码路径上，但 pak 里 `datas/sound.ini` 存在且能正常解出。
- 该文案对**任何**能越过表检查的 pak 都会出现，且与 pak 结构、体积、压缩方式、
  条目集合均无关 → 更像是"表通过之后必然会走到的另一个失败分支"，而不是我们改坏了 pak。
- 客户端被 HProtect 加壳（节名乱码、字符串只在运行时可读），静态 xref 不可用；
  本机 `OpenThread` 被安全策略拦截（err=87），栈回溯暂未取到。

## 7. 建议的下一步

1. 用管理员权限/关闭安全策略后跑 `tools/stack_probe.py`，抓弹窗线程栈，定位调用点。
2. 或者用 `MiniDumpWriteDump` 全内存转储 + 现有 minidump 工具链走栈。
3. 若确认是"角色选择界面资源加载失败"，则问题不在 datas.pak，而在
   `Data\*.pak`（71 个）里某个资源包或缺失的 `*.gl` 索引（本客户端 0 个 .gl）。
4. 拿到真正的 3.0.0.2606 配套 datas.pak（不是 QQ 群那份 572 步长的）可直接替换验证。
